# 功能规格：AI 客服 Agent 平台 — 自包含 Web Demo

**Feature 目录**: `specs/001-ai-cs-agent-web-demo`
**代号**: ai-cs-agent（web demo 里程碑）
**创建日期**: 2026-07-29
**状态**: Draft（规格已生成，待 `/speckit-plan`）
**上游共识**: `docs/00-设计共识.md`（13 项已锁定决策 + MVP 边界）

**输入摘要**: 一个独立部署、可开源的多租户 AI 客服 SaaS 的第一个里程碑——自包含 web demo。端到端跑通「用户提问 → 混合检索知识库 → AI 流式回答 → 答不出触发转人工 → 坐席工作台接管回复 → 用户侧实时收到」。demo 用中/英双语通用泛例 FAQ，不碰任何真实线上流量。

## Clarifications

### Session 2026-07-29

- Q: 转人工的「置信度不足」如何判定？ → A: 混合信号——检索最高相关分低于阈值 **或** 模型显式输出「无法回答/需转人工」标记，任一命中即触发转人工。
- Q: 噪音消息（问候/单符号/表情）如何前置识别？ → A: 规则前置——按文本长度、纯符号、纯表情、问候语白名单命中即回固定话术，不进 LLM；未命中者才进入检索/生成。
- Q: 会话状态与历史的持久化边界？ → A: MySQL 为持久事实源（会话与消息落库），Redis 仅承载实时 pub/sub 与在线状态；断线/刷新从 MySQL 恢复历史。
- Q: demo 坐席认证形态？ → A: 预置账号（用户名+口令）+ 会话令牌，单一默认坐席；非匿名但不做自助注册与 RBAC。
- Q: 转人工后无坐席在线/超时如何处理？ → A: 会话进入待接管队列并向用户显示「正在为您转接人工，请稍候」；demo 不做超时自动关闭或自动兜底话术。

## 用户场景与测试（必填）

### 角色

- **终端用户（End User）**：通过网页 widget 提问的访客，匿名或带外部标识。
- **坐席（Agent）**：登录坐席工作台，监看会话、在 AI 答不出或用户要求时接管人工回复。
- **运营/管理员（Admin）**：配置租户、知识库、接入渠道；demo 阶段可与坐席同人。
- **系统集成方（Integrator）**：通过通用 Webhook 把外部渠道消息接入平台。

### User Story 1 — 用户提问获得 AI 流式回答（优先级：P1）

终端用户在网页 widget 输入一个 FAQ 范围内的问题（中文或英文），系统检索知识库并以流式方式逐字返回答案。

**为什么是这个优先级**：这是产品的核心价值主张与「不翻车」底线；没有它其余功能无意义。可独立演示——只要知识库有内容即可跑通问答闭环。

**独立测试**：预置一条泛例 FAQ，打开 widget 提问，观察是否检索到正确条目并流式输出答案。

**验收场景**：

1. **Given** 知识库含「如何重置密码」条目，**When** 用户用中文问「怎么重置密码」，**Then** widget 流式显示基于该条目的答案，首个字符在 2 秒内出现。
2. **Given** 同一知识库，**When** 用户用英文问「how do I reset my password」，**Then** 返回等价的英文答案。
3. **Given** 一次问答完成，**When** 用户追加追问，**Then** 系统在同一会话上下文内继续应答。
4. **Given** 检索命中多条相关条目，**When** 生成回答，**Then** 答案综合最相关内容且不虚构知识库外事实。

### User Story 2 — 答不出触发转人工并由坐席接管（优先级：P1）

当 AI 对问题没有足够置信度或用户明确要求人工时，会话转入待接管队列；坐席在工作台看到该会话、接管并回复，用户侧实时收到坐席消息。

**为什么是这个优先级**：转人工是「AI 客服可上线」的安全阀，也是本里程碑相对上一代（未验证即上线而翻车）的关键差异点。与 US1 共同构成可录屏的完整演示链路。

**独立测试**：提问一个知识库无法覆盖的问题，验证会话进入待接管、坐席接管后双向消息实时互通。

**验收场景**：

1. **Given** 用户问了知识库覆盖不到的问题，**When** AI 置信度低于阈值，**Then** 会话状态转为「待人工」并进入坐席工作台会话列表。
2. **Given** 用户在对话中输入「转人工/talk to a human」，**When** 系统识别该意图，**Then** 立即转入待接管，不再由 AI 应答。
3. **Given** 一个待接管会话，**When** 坐席点击接管，**Then** 会话归属该坐席，AI 停止自动回复。
4. **Given** 坐席已接管，**When** 坐席发送一条回复，**Then** 用户 widget 在 2 秒内实时显示该消息，且标注来源为人工。
5. **Given** 坐席已接管的会话，**When** 坐席选择切回 AI，**Then** 后续消息重新由 AI 应答。

### User Story 3 — 坐席工作台会话监看与切换（优先级：P2）

坐席登录工作台，看到实时更新的会话列表（含状态：AI 应答中 / 待接管 / 人工中 / 已结束），点击任一会话查看完整消息历史，并可在 AI↔人工之间切换该会话的应答方。

**为什么是这个优先级**：US2 已包含「接管+回复」的最小切换；本故事把它扩展为可用的多会话监看面板，是坐席实际可用的前提，但可在核心闭环跑通后补齐。

**独立测试**：制造多个并发会话，验证列表实时刷新、状态正确、点击可查看历史与切换应答方。

**验收场景**：

1. **Given** 存在多个进行中会话，**When** 坐席打开工作台，**Then** 列表按状态与最近活动展示，且新消息到达时实时更新未读标记。
2. **Given** 坐席选中一个会话，**When** 查看详情，**Then** 完整时间序消息历史可见，每条标注来源（用户/AI/坐席）。
3. **Given** 一个 AI 应答中的会话，**When** 坐席主动接管，**Then** 该会话切为人工模式且从待接管计数中移除。

### User Story 4 — 配置租户 / 知识库 / 接入渠道（优先级：P2）

管理员通过管理端维护三张核心配置：租户（工作区）、知识库条目、接入渠道；知识库条目录入后可被检索问答使用。

**为什么是这个优先级**：demo 需要至少一份可检索知识库才能演示 US1；但录入方式可先用最小表单/导入，精细化管理不属于本里程碑。

**独立测试**：新建一条知识库条目，随后在 widget 提问命中该条目，验证配置生效链路。

**验收场景**：

1. **Given** 一个租户，**When** 管理员新增一条 FAQ 知识条目，**Then** 该条目在短时间内可被检索命中。
2. **Given** 已有条目，**When** 管理员编辑或删除，**Then** 后续问答反映最新内容。
3. **Given** 管理端所有操作，**When** 在租户 A 下进行，**Then** 数据不泄漏到租户 B（行级隔离）。

### User Story 5 — 通用 Webhook 接入外部渠道（优先级：P3）

集成方将外部渠道的用户消息以通用 Webhook 投递到平台，平台按同一问答/转人工链路处理并可回投结果。

**为什么是这个优先级**：验证「渠道抽象层」骨架，证明架构可扩展；但 web widget 已足以演示核心闭环，Webhook 属加分项。

**独立测试**：用一段脚本模拟外部渠道 POST 一条消息，验证平台按 RAG/转人工链路处理并可取回应答。

**验收场景**：

1. **Given** 已配置的通用 Webhook 渠道，**When** 外部投递一条用户消息，**Then** 平台创建/续接对应会话并按同一引擎处理。
2. **Given** 非法或无法归属租户的投递，**When** 平台校验失败，**Then** 拒绝并返回明确错误，不产生脏会话。

### 边界情况

- 噪音消息（如「hi」「?」「表情」）：需被低成本识别/路由，不应无谓全量走 LLM。
- 用户在 AI 流式输出中途继续发消息：应有明确的排队或打断策略。
- 坐席接管期间 AI 不得抢答；待接管会话在无坐席在线/超时时保持排队，并向用户显示「正在为您转接人工，请稍候」，demo 不做超时自动关闭。
- WebSocket 断线重连：用户刷新页面后应能恢复当前会话上下文。
- 知识库为空或检索零命中：应稳定走「转人工/兜底话术」，不得报错或杜撰。
- 同一用户多标签页/多设备并发会话的归属。
- 超长输入、超长知识条目、超出模型上下文时的截断与降级。

## 需求（必填）

### 功能需求

- **FR-001**：系统必须接受终端用户经网页 widget 提交的中文或英文文本问题，并维持同一会话的多轮上下文。
- **FR-002**：系统必须对用户问题在知识库上执行混合检索（语义 + 关键词）并对候选结果重排，取最相关内容作为回答依据。
- **FR-003**：系统必须以流式（逐步可见）方式向用户返回 AI 生成的答案，且答案不得虚构知识库之外的事实性内容。
- **FR-004**：系统必须在 AI 置信度不足或用户明确请求人工时，将会话转入「待人工」状态并进入坐席工作台队列。置信度不足的判定采用混合信号：检索最高相关分低于阈值**或**模型显式输出「无法回答/需转人工」标记，任一命中即触发。
- **FR-005**：系统必须允许坐席接管待接管会话；接管后 AI 停止自动应答，改由坐席回复。
- **FR-006**：系统必须把坐席回复实时推送到对应用户 widget，并在消息上标注来源（用户 / AI / 坐席）。
- **FR-007**：系统必须支持在单个会话上于 AI 应答与人工应答之间切换，切换即时生效。
- **FR-008**：坐席工作台必须实时展示会话列表及其状态（AI 应答中 / 待接管 / 人工中 / 已结束），并支持查看单会话完整消息历史。
- **FR-009**：管理端必须支持对租户、知识库条目、接入渠道三类配置的创建、查看、修改、删除。
- **FR-010**：所有业务数据必须以租户（工作区）为粒度行级隔离；任一操作不得跨租户读写数据。开源单机部署默认存在一个内置租户。
- **FR-011**：系统必须提供通用 Webhook 接入点，使外部渠道消息经同一问答/转人工链路处理，并对非法/无法归属的投递返回明确错误。
- **FR-012**：系统必须对明显的噪音消息（问候语、单符号、纯表情等）提供前置的低成本识别/路由，避免其全量进入昂贵的生成流程。识别采用规则前置（文本长度、纯符号、纯表情、问候语白名单）：命中即回固定话术不进 LLM，未命中者才进入检索/生成。
- **FR-013**：系统必须在检索零命中、知识库为空或生成失败时，稳定降级到「转人工」或兜底话术，绝不报错崩溃或杜撰答案。
- **FR-014**：整套系统必须可由单条一键启动命令在本地拉起全部依赖，启动后可直接在浏览器打开 widget 完成端到端演示。
- **FR-015**：用户 widget 在网络断开重连或页面刷新后，必须能恢复当前会话的上下文与历史；会话与消息以持久存储为事实源，实时通道仅用于在线推送，恢复时从持久存储回读历史。
- **FR-016**：架构必须为「工具调用/办事能力」预留扩展位（本里程碑不接真实工具），使第二期可在不重构核心链路的前提下接入。

### 关键实体

- **租户（Tenant/Workspace）**：隔离边界；拥有其下全部知识库、渠道、会话、坐席。
- **知识库条目（KnowledgeItem）**：一条可检索的 FAQ/知识，含文本、语言、元数据；向量表示与文本分别存放但逻辑关联。
- **渠道（Channel）**：消息来源接入配置（web widget / 通用 Webhook / 未来适配器骨架）。
- **会话（Conversation）**：一次持续的用户-系统交互，含状态（AI/待接管/人工/结束）、归属坐席、所属渠道与租户。
- **消息（Message）**：会话内单条消息，含来源（用户/AI/坐席）、内容、语言、时间戳。
- **联系人（Contact）**：外部用户标识到平台内部联系人的映射。
- **坐席（Agent）**：可登录工作台、接管并回复会话的人。
- **机器人配置（Bot/Agent Config）**：某租户的模型、提示词、护栏、检索策略等应答配置。
- **工具（Tool，占位）**：第二期的办事能力定义；本里程碑仅保留结构占位。

## 成功标准（必填）

### 可度量结果

- **SC-001**：单条一键启动命令后，未做额外手工配置即可在浏览器打开 widget 并成功完成一次问答，全程无需阅读源码。
- **SC-002**：对预置泛例 FAQ 覆盖范围内的问题，中文与英文各一组测试问题的正确检索+作答比例 ≥ 90%。
- **SC-003**：AI 回答的首个可见字符在用户提交后 2 秒内出现（流式起始延迟）。
- **SC-004**：知识库无法覆盖的问题 100% 触发转人工，绝不出现杜撰式硬答或系统报错。
- **SC-005**：坐席在工作台接管后发送的回复，用户侧在 2 秒内实时可见。
- **SC-006**：管理员新增一条知识条目后，该条目可在 1 分钟内被检索命中。
- **SC-007**：跨租户数据隔离在测试中零泄漏——租户 A 的任何数据在租户 B 上下文中均不可见。
- **SC-008**：完整演示链路（提问→检索→流式答→转人工→坐席接管→用户实时收到）可一次性连续录屏完成，无需人工重启或规避步骤。

## 假设

- 采用共库 + 租户标识的行级隔离；开源单机部署等同于一个默认租户，与多租户同一套代码路径。
- LLM 能力经统一的模型网关提供，可切换后端模型；demo 阶段的模型选择不影响功能验收标准。
- demo 知识库为租户中立的通用泛例 FAQ，中/英双语；阿拉伯语/乌兹别克语等多语言检索效果不在本里程碑验证。
- 坐席身份认证采用预置账号（用户名+口令）+ 会话令牌，单一默认坐席；非匿名但不做自助注册与精细化 RBAC。
- 「置信度不足」的判定阈值与噪音识别策略允许在实现期以最简形式落地，只要满足 FR-004/FR-012/FR-013 的可观察行为。
- 实时性目标（2 秒级）针对本地/演示环境；生产级 SLA 待接入期另定。
- 会话与消息以关系存储为持久事实源，缓存/实时通道只承载在线态与推送；断线恢复从持久存储回读。

## 范围

### 本里程碑内（In Scope）

- 租户 / 知识库 / 渠道三张配置
- 知识库混合检索（语义 + 关键词）+ 重排
- RAG 应答引擎（预留工具节点）
- Web widget 流式问答
- 坐席工作台（会话列表 / 接管 / 转人工 / AI↔人工切换）
- 通用 Webhook 接入
- 一键启动的本地全依赖编排
- 中 / 英双语泛例 FAQ

### 本里程碑外（Out of Scope）

- 工具调用/办事能力的真实接线（仅占位）
- livchat 真实渠道适配与其历史落库
- 灰度 / 影子 / 审核模式
- 飞书、WhatsApp、Telegram 的真实接通（仅留适配器骨架）
- 阿拉伯语/乌兹别克语等多语言检索效果验证
- 精细化 RBAC、计费与配额

## 依赖

- 一套可用的 OpenAI 兼容 LLM 网关（含 embedding 能力）。
- 向量检索、关系存储、缓存、实时消息通道等基础组件均由一键编排在本地提供，无需外部托管服务。
- 上游 `docs/00-设计共识.md` 中的 13 项决策为本规格的既定约束。
