# AI 客服 Agent 平台 — 设计共识

> 日期：2026-07-29
> 状态：需求澄清完成（grill-me 逐项拍板），待进入 Spec 流程
> 代号：ai-cs-agent（暂定）

## 一句话定位

一个**独立部署、可开源的多租户 AI 客服 SaaS**。第一个里程碑是一个自包含的 **web demo**，端到端跑通「用户提问 → 检索知识库 → AI 回答 → 转人工 → 坐席接管」。livchat 是它的第一个真实租户，但接入放在 demo 跑通之后。

## 背景

- 起点：`customer_service_opt` 项目已完成 livchat 客服数据调研 + 30 天会话分类。关键事实：
  - livchat 月约 32 万条用户提问 / 18 万用户 / 20 万会话；**76% 是 "hi"/"?"/表情 等噪音**。
  - 实质问题中**支付/充值域占近一半**（充值不到账、金币未到账、退款、支付失败），其次账号删除、通话问题、免费金币索要、主播投诉。
  - 多语言：英 / 阿拉伯 / 乌兹别克 / 西 / 法 混合。
  - 上一代 AI 回复（腾讯 Desk）**msg_source=1 自 2026-04-29 起零落库、直接停摆**——推测是「未经验证就上线、翻车后被关」，本项目须避免重蹈覆辙。
- 开发者：单人/小团队，Python + Java 背景，重视可维护性与「跑通真实需求」，反对投机性重构。

## 已锁定的 13 项决策

| # | 决策项 | 结论 |
|---|--------|------|
| 1 | 定位 | 独立可开源 SaaS，livchat 是第一个租户（非唯一目标） |
| 2 | 技术栈 | Python 3.11+ / uv / FastAPI / Redis / MySQL + Qdrant；LLM 走 OpenAI 兼容网关（new-api，可调 deepseek/claude/gemini） |
| 3 | 实时通道 | 主流分工：用户 widget 走 **WebSocket**、渠道走 webhook、管理端走 REST |
| 4 | 引擎形态 | **分期**：MVP 纯 RAG + 转人工；架构预留工具调用位（第二期接「办事」能力） |
| 5 | 知识库 | **Qdrant** 向量库，混合检索（向量+关键词）+ 重排，多语言 embedding；靠 docker-compose 打包保「开源易部署」 |
| 6 | 多租户 | 共库 + `tenant_id`(workspace) 行级隔离，中间件统一注入；开源单机 = 一个默认租户，同一套代码 |
| 7 | 转人工 | **平台自带坐席工作台**（会话列表 + 接管回复 + AI/人工切换） |
| 8 | 坐席前端 | 独立 **React + TS + Vite** SPA |
| 9 | 首批 channel | 抽象层容纳四类；先做实 **通用 Webhook/REST + Web widget**，飞书 / WhatsApp/Telegram 留适配器骨架按需接 |
| 10 | 上线策略 | **先做 web demo 版**，不碰 livchat 线上流量；灰度（影子/审核）推到接入期 |
| 11 | demo 知识库 | 租户中立的**通用泛例 FAQ** |
| 12 | demo 语言 | 先**中/英双语**；多语言 embedding 能力架构预留 |
| 13 | 编排 & 仓库 | **LangGraph**（约束在薄层，不渗进领域逻辑，保留可替换性）；**新建独立仓库** |

## MVP（web demo）边界

**做**：
- 租户 / 知识库 / channel 三张配置
- Qdrant 混合检索（向量 + 关键词）+ 重排
- LangGraph RAG 引擎（预留 tool 节点）
- Web widget（WS 流式输出）
- 坐席工作台（会话列表 / 接管 / 转人工 / AI↔人工切换）
- 通用 Webhook 接入
- docker-compose 一键起（含 Qdrant / MySQL / Redis）

**不做**：
- 工具调用真实接线
- livchat 融云适配与 customer_queue 落库
- 灰度 / 影子模式
- 飞书、WhatsApp/Telegram 真实接通（仅留适配器骨架）
- 多语言（阿/乌）验证
- RBAC 精细化、计费配额

**验收标准**：
`docker compose up` 后，浏览器打开 widget，用中/英问泛例 FAQ 里的问题 → 被正确检索并**流式回答**；答不出时**触发转人工** → 坐席在工作台看到会话并**接管回复** → 用户侧**实时收到**。整条链路可演示、可录屏。

## 领域模型（初稿，待 Spec 细化）

```
Tenant/Workspace ──┬── Channel（webhook / widget / 飞书 / whatsapp...）
                   ├── KnowledgeBase ── KnowledgeItem（向量在 Qdrant，文本+元数据在 MySQL）
                   ├── Bot/Agent（模型、prompt、护栏、检索策略配置）
                   ├── Conversation ── Message（含 role/source/content/lang/ts）
                   ├── Contact（external_user_id ↔ 平台 contact 映射）
                   └── Tool（第二期：function schema → HTTP/OpenAPI/MCP，MVP 仅占位）
```

所有业务表带 `tenant_id`，查询经中间件统一注入租户上下文。

## 主要风险与已知未知

- **LangGraph 与「单人维护、别上重框架」有张力**：约束在薄层，领域逻辑不依赖它，保留替换余地。
- **Qdrant 增加部署负担**：用 docker-compose 打包兜底「一键起」承诺。
- **多语言检索效果**（阿拉伯/乌兹别克）demo 阶段不验证，接入 livchat 前必须补验。
- **噪音消息（76%）成本**：需前置便宜的过滤/路由层，避免噪音全量走 LLM（架构预留，MVP 可简化）。
- **转人工 + 坐席工作台显著放大范围**：实时消息前端是工作量大头，需在 Spec 里严控 MVP 范围。
